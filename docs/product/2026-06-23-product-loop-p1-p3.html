1. 背景与解决的问题

改造前，产品轨在「DEFINE 5 问访谈 → 生成产品定义 → 写 draft-spec.md → 弹一句 toast」后流程终止，且两个确诊问题：

  • 产物看不见：spec 写到磁盘但 UI 从不回显、无打开入口，且 .kunpeng/product/ 未纳入 git。
  • 到 spec 断头：spec 之后没有通向设计、代码、验证的路径，鲲鹏明明有成熟的 kunpeng plan/run/design loop 却没接上。

行业（Amazon Working Backwards、OpenSpec、spec-driven development）的核心规律一句话：机器自动生成下一份产物，人来把关接受（auto-generate, human-gate）；每份产物是仓库里可见可编辑的文件。P1–P3 即把这条规律在鲲鹏落地。

2. 架构总览

2.1 五段状态机（脊柱）

一个持久化、纯函数、不可变的阶段机（src/product/stage-machine.ts）：

ProductStage = "define" | "spec" | "design" | "build" | "validate"
StageStatus  = "pending" | "drafted" | "accepted"

ProductLoopState = {
  slug, idea, currentStage,
  stages: { [stage]: { status, artifactPath, updatedAt } }
}

转移规则：机器自动起草下一份草稿产物（drafted）→ 人看 / 改 / 点「接受」→ 推进到下一段并自动起草其产物。validate 段的 pivot 裁定会把 currentStage 拨回（resetToStage），形成闭环。

2.2 产物存储（修掉"看不见"、纳入 git）

文件阶段说明
.kunpeng/product/<slug>/state.json全程阶段机状态
spec.mdSPECPR/FAQ + Gherkin，UI 可见可编辑
brief.jsonDESIGN由 spec 推导的 10 字段设计 BRIEF
build-spec.mdBUILDagent 把 Gherkin 改写成 plan 能吃的可构建 spec
validation.jsonVALIDATE信号 + 裁定 + 闭环动作

文本产物全部纳入 git 跟踪（源真相不可静默消失）；可再生二进制（设计预览 PNG .kunpeng/design-out/、previews/）保持 gitignore。

2.3 核心模式：auto-generate + human-gate

机器起草下一份产物（agent 或纯函数）→ 落成仓库可见可编辑文件 → 人在 cockpit 里看 / 改 / 点接受 → 才推进。plan / run 等"会真改代码"的重动作始终在人工门之后，防止照 LLM 幻觉施工。

3. 三个阶段的能力

P1 · 闭环骨架（DEFINE → SPEC → DESIGN） · main 1cae0c4

  • cockpit「产品」tab 重写为 stepper（顶部分段进度条 + 当前阶段产物 + 单一主操作）。
  • 访谈完成 → 自动起草 spec（drafted）；spec 在 UI 内可见、可编辑、可保存、可接受。
  • 接受 spec → 自动推导 10 字段设计 BRIEF → 跑既有 design loop 出可视预览。

P2 · 接 dev 构建（+ BUILD） · main 9e29d2f

  • 核心缺口：自动起草的 spec 末尾 accept 是占位符，kunpeng plan/run 吃不了（缺单 H1 分段 / scope 块 / 可执行 accept 三项硬要求）。
  • spec-to-buildspec.ts：agent 把 PR/FAQ + Gherkin 改写成可构建 spec（单 H1、每行 allow: 的 scope 块、由场景推导的可执行 accept）。
  • 人精修接受 → 后台跑 kunpeng plan 拆 flow（flow 复用现有「开发流」tab 展示）。真正 kunpeng run 出代码不自动触发，人在 plan 与 run 之间留门。
  • 诚实风险设计进去：Gherkin 是 LLM 编的，可能引用幻觉接口 → 人工精修门是防照幻觉施工的关键，不可跳过。

P3 · 验证闭环（+ VALIDATE） · main c8caa59

build（plan 出 flow，人看结果/预览） │ 接受 → 进 validate ▼ validate：人录入真实信号（遥测/真访谈/销售）+ 假设 + 裁定 │ validateProduct() —— 无真信号 → 强制 inconclusive（不许裁定） ▼ closeValidationLoop() ├─ persevere → 闭环完成（可交付），决策落 ADR + KB ├─ pivot → nextSeed 全自动重跑 spec→design→build 重生下游，拨回 build:drafted 给人最后审 └─ inconclusive / gather-signals → 留在 validate，提示补真实信号
  • 真信号门（复用 validateProduct）：合成用户 / 空信号绝不能裁定 pivot·persevere，强制 inconclusive。
  • pivot 全自动重生：applyPivot 用 nextSeed 链式 agent（autoDefine → definitionToSpec → specToBrief → specToBuildSpec）重生 spec/brief/build-spec，拨回 build:drafted。plan/run 仍人工门。
  • 决策落项目 ADR（docs/decisions/）+ 沉淀知识库（best-effort）。

5. 设计原则

  1. auto-generate, human-gate：机器起草、人接受才推进。
  2. 产物即文件：每份产物是仓库可见可编辑文件，文本进 git。
  3. 真信号才裁定：合成/空信号强制 inconclusive。
  4. 幻觉防线：pivot 可全自动重生下游，但 plan/run 始终在人工门之后。
  5. dogfood：复用鲲鹏自身 plan/run/design loop，不重造拆解器。

6. 验证强度（每阶段）

  • 单元测试 + tsc0 + build0（P3 收口 35+ 产品测试绿）。
  • 真 agent e2e（防 fake 命门）：P2 = 真 CliRunner 起草 build-spec → 真 parseMethodPlan 拆出带可执行 accept 的 flow；P3 = recordAndClose → applyPivot 真重生（2 次真 agent），build-spec 被新种子重写、拨回 build:drafted。
  • UI 浏览器截图视觉验证（5 格 stepper、表单、诚实提示）。
  • opus 终审把关：抓到并修复 client.ts 模板字面量 \n 转义 Critical（会让整个 cockpit SPA 崩）。

7. 过程教训（已沉淀知识库）

  1. client.ts 模板字面量转义坑会复发：clientScript 整体是 TS 模板字面量，源码 \n 编译期被吃 → 浏览器端字符串跨裸换行 → new Function 抛 SyntaxError → 全站崩。手改 client.ts 后必 new Function(clientScript) 校验；转义符双反斜杠。
  2. 真 agent e2e 是防 fake 命门：fake 单测会掩盖 wiring，合并前必真 CliRunner 串真组件。
  3. 移动靶 main 的干净 ff：独立 worktree rebase 到最新 main → 在持有 main 的 worktree merge --ff-only（被抢自动拒绝防 clobber）→ 紧凑"再 rebase + 立即 ff"窗口内抢进。
  4. 共享树部署遇别人 WIP：git stash 暂存（可恢复不丢）→ merge → 部署 → 通知原主去 stash 捞，绝不 discard。
  5. 并行 subagent 提速：独立任务（不同文件无 import 依赖）一条消息多 agent 并发；有依赖链串行；后台 agent 改 http.ts 时主会话同时手改 UI 真并行。
  6. 合并卫生：合前必 rebase/fold 最新 main、绝不 git add -A、只显式路径（见多起 stale-base clobber 事故）。
