01

产品摘要（现在的鲲鹏）

鲲鹏当前不是单纯 coding agent，而是一个本地研发编排器：把需求、执行、验证、人工门、发布、经验沉淀串成流程。
产品类别
本地 AI 研发控制塔（雏形）。用 CLI 启动任务，用 cockpit 观察确认，用 artifact 记录产物，用 guard/evidence 证明结果。
核心价值
把 agent 输出变成可合并状态。重点不是"生成代码"，而是从需求推进到验证通过、人类确认、可发布、可复盘。
当前阶段
能跑的控制塔雏形——已有命令、artifact、worktree、guard、release、自进化提案、web cockpit；产品体验需收束成 P0 切片。
02

目标用户

当前最适合先服务个人开发者和一人多项目维护者。企业团队协作是后续扩展，不是 P0。
主用户 · 独立开发者 / Solo Founder
  • 同时维护多个产品、网站、自动化脚本、工具库；已用 AI 编码工具，但缺统一控制、验证和沉淀。
  • 关心本地数据、账号登录态、成本、回滚。
  • 核心痛点：AI 做了很多，但我仍要收尾——不知道 agent 真做到哪步、不知道测试/lint/构建/发布是否真过、每次都要重复解释项目背景、失败经验没自动变成下次的护栏。
03

当前已有能力

以下来自当前仓库代码与文档，不是未来想象（本阶段 600+ 测试全绿、claude/codex 双后端 verified）。
模块已有能力用户价值成熟度
CLIrun/register/projects/onboard/compile/guard/evolve/release/serve 等命令行登记、接管、跑任务、体检、发布、启动总控台可用，需更强引导
Artifact标准产物：spec/plan/task/review/experience/proposal/release流程不靠聊天记忆，重要状态落盘可追踪基础成熟
Flow State记录阶段、人工门、运行状态，供 dashboard 读cockpit 反映真实执行状态向真数据全视图硬化中
Worktree 隔离按 flow 分配独立 git worktree，守单写者减少并行冲突，保护主工作区核心已在
Agent Runner登录态 CLI 后端，claude/codex 可切换不必暴露 API key，用现有 agent 工具可用，仍依赖供应商 CLI
Guard只读体检：typecheck/lint/TODO 扫描，存 review确定性质量扫描，减少"看起来完成"需接更真实测试信号
Release跑 build，成功记 release ready、失败记 rolled-back发布前验证纳入闭环基础可用
Self-evolution消费 experience 生成 proposal，仅改 conventions、拒 core、需人工门失败经验变改进建议，不自动越权缺公开可复现曲线
Web Cockpit多项目状态、红绿灯、agent 阶段、ETA、卡点、人工门操作不只看 CLI，可在页面观察确认雏形，需强化真实任务视图 + review inbox
04

核心对象模型

产品体验应围绕这些对象组织，而不是暴露过多内部实现。
对象含义说明
Project被鲲鹏管理的项目路径、展示名、自描述、健康状态、活跃 flow、人工门
Flow一次需求执行从需求 → 计划 → 实现 → 验证 → 人工门 → 合并/回滚
Artifact流程真相源spec/plan/task/review/experience/proposal/release，可查看可引用
Evidence完成证明测试/lint/typecheck/build/diff/人审，证明不是口头完成
Gate人工门高风险动作、人审合并、自进化应用、发布动作需人类确认
Experience经验沉淀失败原因、重复模式、修复方式、防复发建议——自我进化的原料
05

当前缺口

这些缺口是让鲲鹏从"能跑的工程系统"变成"用户可理解产品"的关键。
缺口 1 · 产品入口偏工程化
命令很多，但用户每天真正需要的是"现在哪些任务需要我处理"。cockpit 要把命令能力翻译成工作台语言。
缺口 2 · 验证证据待产品化
用户需要在页面看懂任务为什么可以合并，而不是只看到命令退出码。
缺口 3 · 研发记忆输入层未实现
现有 knowledge 更偏 experience，不支持文章/PDF/聊天/竞品/报警等输入。
缺口 4 · 自我进化缺效果曲线
已有 proposal 和证据闸基础，但需 eval-runner 证明改进前后真的更好。
06

下一步 · P0 产品需求（7 天切片）

不扩大战略，而是做一个可演示、可验证、可复盘的 P0 产品切片。围绕一条流程，而非命令列表。
01 登记项目
02 接管上下文
03 提交需求
04 隔离执行
05 验证证据
06 人工确认
07 发布沉淀
需求说明验收标准
真实 Flow 工作台首页显示真实运行中的 flow、阶段、状态、卡点、ETA启动一条真实任务后，cockpit 能实时反映阶段变化
Review Inbox统一展示等待人类确认的合并、发布、proposal用户在一个页面看懂"为什么需要确认"和"确认后发生什么"
Evidence View展示测试、lint、typecheck、build、diff 和失败摘要每个完成任务能打开证据详情；失败任务有归档原因
Experience 自动沉淀失败和人审反馈能生成 experience 草稿至少一种失败能自动转成可读 experience artifact
Proposal / Skill 草稿从 experience 生成改进建议或 skill 草稿，但不自动应用用户能在人工门里批准或拒绝提案
★ P0 一句话验收
拿一个真实项目跑一条真实需求，鲲鹏能在 cockpit 里展示从需求、执行、验证、人审到经验沉淀的完整链路，并且用户能判断它是否可以合并。
07

P0 之后 · 30 / 60 / 90 天增量

每步都让"可验证控制塔"更真实，不扩战线。与战略 V4 路线图对齐。
30 天 · 闭环硬化
补 review inbox、可编辑 plan 门、验证证据详情、失败复盘、release/rollback 视图。
验收：声明完成=真实通过率 ≥ 80%；失败都有可归档原因。
60 天 · Knowledge Inbox v1
kunpeng capture；URL/文本/文件/截图/聊天片段捕获；自动摘要/标签/项目关联/带引用检索；人工 promote。
验收：五个高频场景至少跑通三个。
90 天 · 自我进化曲线
eval-runner 回放 holdout，比较提案前后质量与成本，形成可复现报告。
验收：至少一条自我增强曲线可被本地重跑验证。
08

Cockpit 页面需求

cockpit 已有基础（多项目侧栏、运行真相、自进化页、全交互按钮、a11y 已修），下一步让它成为用户每天打开的工作台。
首页 · 跨项目工作台
  • 全部项目健康状态
  • 正在运行 / 失败 / 等待人审 / 可发布的任务
  • 最近产生的 experience 和 proposal
  • 突出"现在需要我做什么"
项目页 · 项目内研发视图
  • 开发流：flow 阶段、日志、证据、分支
  • 方案：plan、可编辑计划门、启动 run
  • 产品：DEFINE 阶段和需求澄清（访谈已接通）
  • 设计：design preview / codegen / visual evidence
Review Inbox · 统一人审入口
  • 合并确认 · 发布确认
  • proposal 批准
  • 高风险 connector 动作确认
Evidence View · 验证证据详情
  • 测试命令和输出摘要
  • lint / typecheck / build 结果
  • diff 风险提示
  • 失败原因和下一步建议
