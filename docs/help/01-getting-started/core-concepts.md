# 核心概念

理解下面几个概念后，你就能读懂鲲鹏的一条需求怎样从方案走到等待合并。

## 方案（spec）

方案是一次研发工作的起点，也是工作范围和完成条件的事实来源。

一份有效方案至少要说清楚：要做什么、为什么做、允许修改什么，以及怎样算做对。

方案不是实现笔记，也不是让实现者自由解释的愿望清单。

它应把关键结果写成可检查的契约，避免执行过程中为了“跑绿”而降低目标。

## 验收命令（accept）

accept 是方案作者给出的客观、可执行判定。

它可以运行真实测试、类型检查、lint，或直接检查产物的具体形态和行为。

验收命令必须由方案阶段确定，并在实现阶段保持锁定。

实现者不能自行把它换成更弱的命令，也不能只检查“有一个测试文件”之类与真实行为无关的表象。

这种安排把“我觉得完成了”变成可重复执行的证据。

## flow 与 loop

flow 是一条具体需求的工作流。

通常一条需求对应一条 flow；较大的方案可以先拆成多条边界清晰的 flow。

每条 flow 有自己的状态、产物、验证结果和分支，便于追踪它走到了哪一步。

loop 是推动 flow 前进的研发循环。

它把方案转换为实现任务，安排执行，运行验证，并把结果送到下一阶段或人工门。

loop 不是无条件重试；任何完成声明都必须由落盘产物和真实验证证据支撑。

## 隔离 worktree 与单写者

每条 flow 在独立的 git worktree 中工作。

并行 flow 因此拥有彼此隔离的目录和分支，不需要在共享工作树中来回切换。

在任一时刻，一条 flow 的代码写锁只属于一个实现者，这就是单写者原则。

审查者和其他角色可以读取、验证并提出发现，但不能与实现者同时直接修改同一条 flow 的代码。

worktree 解决并行目录隔离，单写者解决同一工作流的修改所有权；两者需要同时成立。

## 三道人工门

鲲鹏只为以下三类动作设置强制人工门：

1. 合并到主干。
2. 修改宪法或角色卡。
3. 对外发布，或操控已登录的第三方后台。

合并会改变共享代码事实，治理修改会固化系统规则，对外发布或第三方操作会影响仓库之外的世界。

因此，这三类动作不能由自动流程自行越过。

实现、验证、写入非主干分支等可逆步骤可以自动推进，但到达上述边界时必须等待人类确认。

## 宪法与跨工具真相源

鲲鹏的治理规则位于仓库的 `constitution/` 目录。

不可变核心定义单写者、产物证据、可逆性、人工门和确定性优先等底线。

可演进约定承载会随实践调整的工程规则，但其固化仍需经过人工门。

编译过程会把这些规则写入 `AGENTS.md`，使不同工具中的 agent 都能读到同一份约束。

因此，`constitution/` 是规则源，编译出的 `AGENTS.md` 是跨工具可消费的真相载体。

不要把会话中的临时说法当作对宪法的替代。

## 差分验证

真实仓库可能在一条新需求开始前就存在测试、lint 或类型检查错误。

如果验证门要求整库从历史红灯一次变成全绿，当前 flow 会被与自身无关的旧问题永久阻塞。

鲲鹏因此使用差分验证：实现前记录基线，实施后再次运行同类检查，只拦截基线之外新增的错误。

差分验证不是忽略错误，也不是把检查改成永远成功。

旧错误仍然可见；当前 flow 只是对自己新引入的问题负责。

任何无法确定是旧错还是新错的情况都应当保守处理，而不是静默放行。

## 确定性优先

能够由文件检查、git、测试、lint 或类型系统回答的问题，应先用这些可重复手段回答。

语言模型适合处理需求理解、设计权衡和确定性工具无法裁定的质量问题。

它不应取代已经存在的客观判定，也不能把未经执行的推测包装成验证证据。

## 一条需求如何前进

最简路径是：编写带 accept 的 spec，创建 flow，由 loop 在隔离 worktree 中安排单写者实现，运行差分验证，再进入合并人工门。

只要记住“方案锁定目标、证据证明结果、人工守住不可逆边界”，就抓住了鲲鹏工作方式的核心。
