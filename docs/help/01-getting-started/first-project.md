# 5 分钟跑通第一个项目

本页用最短路径把一个已有 git 仓库交给鲲鹏纳管，并从一份最小方案创建第一条研发工作流。

开始前，请先完成[安装与运行](install-and-run.md)，并确认目标目录本身是一个 git 仓库。

下文中的 `<目标仓库路径>` 和 `<spec.md>` 都是占位符，请替换为你机器上的实际路径。

## 第一步：登记目标项目

运行：

```bash
kunpeng register --repo <目标仓库路径>
```

`register` 会把目标仓库登记进中央项目注册表，并在目标仓库写入项目自描述信息。

命令是幂等的；对同一个仓库重复登记不会把它变成多个独立项目。

登记完成后，总控台才能把这座仓库作为一个已纳管项目聚合展示。

## 第二步：生成接管声明

运行：

```bash
kunpeng onboard --repo <目标仓库路径>
```

`onboard` 会为已经登记的项目渲染并打印接管声明。

如果项目尚未登记，这一步会失败，因此顺序应当先 `register`、再 `onboard`。

接管声明用于说明方案角色、技术执行和人工门之间的边界。

## 第三步：写一份最小 spec

在合适的位置新建一个 Markdown 文件，例如 `<spec.md>`。

最小示例可以写成：

````markdown
# 补充项目说明
需求：在仓库根目录提供一份简短的项目说明。
验收：说明文件必须真实存在。
```accept
test -f README.md
```
````

这个示例包含一个标题、一句需求和一个可执行的 `accept` 验收命令。

实际工作中，方案还应明确允许修改的文件范围、不可触碰的边界，以及需要保持不变的行为。

accept 要直接检查真实产物或行为，不能只要求“让实现者自行写测试”。

选择验收命令时，应确认它能在目标仓库中真实运行，并且在结果做错时会失败。

## 第四步：创建并运行方案

在目标仓库上下文中运行：

```bash
kunpeng plan <spec.md>
```

`plan` 会读取方案并把它推进到鲲鹏的研发流程中。

不要在已经由鲲鹏创建的 flow worktree 内再次运行 `plan`；工作流内的实现者应直接完成当前任务，避免递归派发。

## 第五步：在总控台观察推进

另开一个终端启动总控台：

```bash
kunpeng serve 7777
```

然后在浏览器打开 `http://localhost:7777`。

你可以从总览或当前项目入口观察 flow 的阶段和状态，并在“待我处理”查看需要人工决定的事项。

实现与验证在隔离 worktree 和非主干分支中进行，不会因为流程自动推进就直接改变主干。

## 第六步：处理合并人工门

当实现通过验证并到达合并边界时，流程会停在合并人工门。

此时应查看方案、改动和真实验证证据，再决定是否允许合并到主干。

鲲鹏不会自动越过这道门；看到“等待处理”不是故障，而是不可逆边界正在按设计生效。

## 完成标志

跑通以下链路，就完成了第一个项目的上手：

1. 目标仓库已登记。
2. 接管声明能够生成。
3. spec 包含真实可执行的 accept。
4. `kunpeng plan <spec.md>` 创建工作流。
5. 总控台能够看到 flow 推进。
6. 通过验证的结果停在合并人工门等待人类决定。
