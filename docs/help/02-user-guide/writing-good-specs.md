# 写好 spec：让范围和验收都可执行

一份好 spec 不是愿望清单，而是实现者能照着做、验证器能客观判断的工作契约。

## 先守住单 H1 结构

多文件 spec 全文只用一个 `#` H1 标题。

正文分节使用 `**背景**`、`**实现要求**` 这样的粗体行，不要使用 `##` 或 `###`。

原因是 `plan` 会按标题层级拆 flow。误用 `##`，可能把本来属于同一项工作的内容拆成没有各自验收命令的 flow；其中任何一条无法验证，整段就会回滚。

普通项目符号可以使用，但不要把正文随手写成会被解析为独立任务的结构。

## 需求要点怎么写

至少回答三个问题：

- **背景**：为什么要做，用户现在遇到了什么问题。
- **改动面**：要新增或修改哪些真实产物，最好点明目录、文件或可观察行为。
- **不改什么**：哪些目录、接口、行为或既有文件必须保持不变。

避免只写“优化一下”“补齐能力”这类无法验真的句子。把目标改写为用户能观察到的结果，例如“缺少配置时命令返回非零状态并打印处置提示”。

## 用 scope 锁住改动范围

在 spec 中加入 `scope` 围栏，每行写一条规则：

```scope
allow: docs/example/**
forbid: src/security/**
```

`allow` 表示本 flow 可以改动的路径，`forbid` 表示明确禁止触碰的路径；路径可以使用 glob。

`allow:` 或 `forbid:` 与路径必须写在同一行，不要改成 YAML 列表。

scope 要覆盖完成需求所需的全部文件，同时尽量保持最小。范围太窄会让必要改动被范围门拦下；范围太大则会放大误改和集成风险。

如果未声明 scope，范围门会直接跳过，越界改动就可能溜进集成。因此，没有 scope 不是“默认更安全”，而是少了一道边界检查。

## 用 accept 写能红能绿的验收

`accept` 围栏里放真实可执行的验收命令：

```accept
test -f docs/example/guide.md
```

好的 accept 必须“能红能绿”：实现前运行应失败，实现正确后运行应成功；如果实现被破坏，再运行还应失败。

优先检查真实文件、真实导出、真实测试或真实运行行为。只检查一段字符串“在场”，往往会让空壳实现也能凑绿。

验收命令还应直接点名新产物，避免测试过滤条件没有命中任何测试却仍返回成功。

## 用 accept-file 锁定作者测试

重要行为可以由 spec 作者直接写成 `accept-file`：

````markdown
```accept-file path=test/example.test.ts
import { expect, test } from "vitest";
import { describeResult } from "../src/example.js";

test("错误输入给出明确结果", () => {
  expect(describeResult("")).toBe("invalid");
});
```
````

验收点名的测试文件由 spec 作者写死。loop 每轮验证前都会把这份内容覆盖落盘，因此实现者不能通过删测试、改期望值或弱化断言来让自己过关。

作者测试应断言具体输入和具体输出，并导入真实实现；恒真断言或“测试存在即可”仍然是弱验收。

## 完整最小 spec 示例

下面是一份可直接改写的最小方案。注意它只有一个 H1，正文分节都用粗体：

````markdown
# 新增项目使用说明

**背景**

新用户进入仓库后不知道如何启动项目，需要一份简短说明。

**改动面**

- 新增 `docs/usage.md`，写明安装条件和启动步骤。
- 文档使用简体中文，命令必须能直接复制执行。

**不改什么**

- 不修改源码和现有测试。
- 不改动仓库根目录的既有文件。

```scope
allow: docs/usage.md
forbid: src/**
forbid: test/**
```

```accept
test -f docs/usage.md && grep -q '启动' docs/usage.md
```
````

这个示例的 accept 适合纯文档产物；涉及代码行为时，应改为运行真实测试或导入真实函数验证，不要停留在字符串检查。

## 常见回滚原因

1. **范围过大**：allow 覆盖了无关目录，执行者顺手改了旁支文件，随后在范围审查或合并审查被拒。把 scope 缩到完成本需求的最小集合。
2. **范围过窄**：实现必须修改的消费者或测试不在 allow 中，范围门判定越界。先查清改动链，再把必要路径明确列入。
3. **验收过弱**：accept 只检查字符串、空测试集或永远成功的命令，无法证明真实行为；审计发现证据无抓力后回滚。
4. **验收锚点漂移**：验收 grep 某个名字，实现者却改名或另放一个同名占位符来凑绿。让 accept 导入真函数、运行具体用例，或用 accept-file 锁定测试。
5. **标题误拆流**：正文使用 `##` 分节，拆出的 flow 没有自己的 scope 或 accept，导致整段回滚。
6. **基线本来就是红的**：改动前仓库已经无法通过既定验证，新 flow 无法证明自己没有引入回归。先恢复基线，再提交功能需求。

提交前可以再问自己三遍：改动边界是否明确，错误实现是否会让 accept 变红，实现者是否无法改写验收标准。三项都能回答“是”，这份 spec 才适合发射。
