# 日常操作 FAQ

下面汇总提交需求、运行 flow、查看结果和处理常见异常时最常遇到的问题。

## 1. 为什么我的流被回滚了？

最常见的原因是验收命令没有通过、改动越出了 scope，或最终改动为空。

先看 flow 的失败阶段和真实命令输出，再核对 spec 是否把必要路径纳入 allow、验收是否能客观判真。不要只根据最后一行摘要猜原因。

## 2. 为什么改动不自动合并到主干？

因为合并主干属于 C5 人工门 #1。

验证通过的结果会留在 `kp/` 分支，等待你在总控台“待我处理”查看 diff 和证据后确认。自动流程不会替你跨过这道门。

## 3. “递归守卫”报错是什么意思？

它表示当前命令运行在鲲鹏创建的 flow worktree 内，而实现者又尝试调用 `kunpeng run` 或 `kunpeng plan` 派发新 loop。

这会造成自指递归，所以被硬拒绝。flow 内的实现者应直接创建或修改当前 scope 允许的文件，不能再次派发鲲鹏 loop。

## 4. 提示 `Not logged in` 怎么办？

先运行账号体检：

```bash
kunpeng account doctor
```

`account doctor` 会检查账号配置指向的凭证目录是否存在、可读且非空。预检通过仍不等于后端授权一定有效；必要时在对应 CLI 中重新登录，再用低风险真实任务确认。

## 5. 怎么换后端？

用 `KUNPENG_BACKEND` 环境变量为当前命令指定 `claude` 或 `codex`：

```bash
KUNPENG_BACKEND=codex kunpeng run "<需求描述>" --accept "<验收命令>"
```

未设置时，系统可以按当前配置和阶段路由。切换后端不会自动修复该后端的登录态或配额问题。

## 6. 怎么看花了多少 token、多少钱？

运行月度费用报表：

```bash
kunpeng cost-report --month <YYYY-MM> --repo <目标仓库路径>
```

报表汇总 token、估算费用和缓存命中情况。金额是按记录计算的估算值，账单事实仍以实际服务商为准。

## 7. “基线红”是什么意思？

基线红表示在当前改动开始前，仓库自身就不能通过既定验证。

这种情况下，新 flow 很难证明失败是旧问题还是自己引入的。应先定位并修复基线，确认同一验证恢复为绿，再提交新的功能改动。

## 8. loop 跑完后改动去哪了？

改动保存在 `kp/` 开头的流分支和对应隔离 worktree 中。

通过验证后，它会出现在合并门等待处理；没有确认合并前，`main` 看不到这些改动是正常现象。

## 9. 能在 Linux 上用吗？

核心 CLI 可以跨平台运行。

后台定时调度当前依赖 macOS 的 `launchd`；在 Linux 上需要自行使用 `cron` 等等价手段安排定时执行，并显式配置运行所需的环境变量。

## 10. 端口被占用了怎么办？

可以先停止占用该端口的进程，或者换一个空闲端口启动总控台：

```bash
kunpeng serve <端口>
```

如果是已在运行的鲲鹏总控台占用端口，先确认没有用户依赖它，再停止旧进程。

## 11. 为什么验收明明“有测试”仍然被判无效？

测试存在不代表测试有抓力。空测试集、恒真断言、只查字符串在场，或者没有命中新测试的过滤条件，都不能证明行为正确。

把验收改成具体输入与具体输出，直接检查真实产物或运行真实测试，并确认破坏实现后它会变红。

## 12. flow 一直显示等待，是不是卡死了？

不一定。它可能正在等待人工门、暂停请求正在下一个阶段边界生效，或后端任务仍在运行。

先在总控台查看当前阶段、待处理事项和最近日志；只有状态与进程证据互相矛盾时，再按[故障排查](troubleshooting.md)处理协调死流或孤儿 worktree。

## 13. 为什么 scope 之外只改了一点也会失败？

scope 是硬边界，不按改动大小放宽。任何未声明路径上的修改都可能影响并发工作或带来隐性回归。

如果需求确实必须触碰该文件，应先修改 spec 明确扩展范围，再重新运行，而不是让实现者“顺手”越界。

## 14. 验证通过是否等于一定可以发布？

不等于。验证只证明既定验收已通过，不能替代对需求理解、真实交互、发布目标和外部影响的判断。

合并、治理固化和对外发布仍要分别经过对应人工门；详情见[三道人工门](human-gates.md)。
