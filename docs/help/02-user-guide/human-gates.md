# 三道人工门：什么时候必须由你确认

鲲鹏会自动推进可逆的实现与验证，但 C5 只允许三类高影响动作停在人工门前：合并主干、固化宪法或角色卡提案、对外发布或操控已登录的第三方后台。

## 人工门 #1：合并主干

flow 验证通过后，改动仍在 `kp/` 分支，不会自动进入 `main`。

打开总控台，点击侧栏的“待我处理”，选择对应项目的合并事项并展开详情。先查看方案范围、改动 diff 和验证证据；确认无误后，点击该事项的合并操作，并按界面提示再次确认合并到 `main`。

合并前至少检查：

- 改了哪些文件，是否每个文件都服务于当前需求。
- 是否有文件越出 spec 的 scope，或出现未声明的删除、重命名。
- 验收命令是否真的执行过，退出状态与输出是否支持“通过”。
- diff 中是否有密钥、冲突标记、二进制或与需求无关的改动。
- 分支基底是否陈旧，合并是否会覆盖主干上的并发更新。

看到“verified”只能说明既定门已经变绿，不代表需求理解、交互效果和集成风险一定正确。自建全绿不等于正确，所以最终合并仍由人判断。

## 人工门 #2：批准自进化提案

鲲鹏可以根据经验提出治理改进，但不能自行把新规则写进宪法或角色卡。

这类事项同样出现在总控台“待我处理”。打开提案后，核对提案 diff、修改理由、触发它的经验来源和可能影响，再决定批准、退回还是暂不处理。

C6 要求自我进化只能提出提案，不能自动固化。原因很直接：一条错误治理规则会影响后续所有 flow，影响面远大于一次普通实现。

批准也不等于盲目接受。若证据来自外部资料，先确认它没有把网页指令、恶意样例或未经验证的结论当成治理事实。

## 人工门 #3：发布确认

任何对外发布，或者操控已登录的第三方后台，都必须在人确认后才继续。

在“待我处理”打开发布事项，核对目标环境、版本或产物、外部影响和回滚办法，再使用事项中的发布确认操作。目标、账号或影响范围不清楚时，不要确认。

这道门覆盖的不只是正式发版。只要动作会改变仓库之外的真实系统，例如使用已登录会话修改第三方后台，也属于 C5 人工门 #3。

## 怎样使用“待我处理”收件箱

“待我处理”是所有人工决策的统一收件箱。侧栏徽标和顶部状态提示会显示待处理数量。

建议按下面顺序逐条处理：

1. 先确认项目、flow 或提案 ID，避免在错误项目上操作。
2. 打开事项详情，读清动作类型：合并、提案批准还是发布确认。
3. 查看 diff、证据、目标与风险，不只看绿色状态标签。
4. 信息完整才确认；证据不足就退回或暂缓，不要替自动流程补猜测。
5. 操作后回到列表，确认该事项状态已经更新，再处理下一条。

批量处理时也应逐项核对。不同事项即使状态相同，scope、证据和外部影响也可能完全不同。

## 为什么不能自动越过

C4 要求自动改动可干净回滚，不可逆动作一律升级为人工门；C5 则把必须确认的动作限定为上述三类。

合并会改变共享代码事实，治理修改会改变系统今后的行为，对外发布会影响真实用户或第三方系统。这些后果不能只靠一次自动验证承担。

人工门不是流程卡住，而是系统在可逆实验和不可逆影响之间停下，把最后的责任与上下文交还给人。
