# 提需求：单需求与方案批量两条路径

鲲鹏接需求有两条常用路径：一句话能讲清的单需求用 `run`，需要拆分和分阶段推进的方案用 `plan`。

## 路径 A：提交一条单需求

在目标仓库中运行：

```bash
kunpeng run "<需求描述>" --accept "<验收命令>"
```

例如，需求描述应说明要得到什么结果；`--accept` 后面则填写能在目标仓库真实执行、能明确返回成功或失败的命令。

`--accept` 不是可有可无的提示。验收命令是这条 flow 判断实现是否成立的唯一客观判据：它必须在结果错误时失败，在结果正确时成功。

如果缺少验收命令，或者命令无论实现好坏都返回成功，系统就无法形成可信证据。流的改动会因此被回滚，而不是带着“不确定”继续向前。这落实了 C3“验证不可伪造”：没有真实验证证据，就不能声明完成。

适合这条路径的需求通常同时满足两点：

- 一句话就能说清预期结果。
- 一条命令就能客观判断结果真假。

## 路径 B：提交一份方案

当工作需要拆成多条 flow 时，先写一份 Markdown spec，再运行：

```bash
kunpeng plan <spec.md>
```

`plan` 会按方案结构拆分工作，并在允许的并发范围内推进多条 flow。每条 flow 仍然需要自己的改动范围和验收判据，不能靠整份方案末尾的一句“测试通过”代替。

需要完整写法时，请继续阅读[写好 spec](writing-good-specs.md)。所有公开命令和参数可查[鲲鹏 CLI 全命令参考](cli-reference.md)。

## 什么时候用哪条路径

用下面的判断即可：

- 一句话能说清，而且验收能由一条命令判定：用 `kunpeng run`。
- 涉及多个文件或多个主题，需要拆分、并行或分阶段：写 spec，再用 `kunpeng plan`。
- 如果需求很短，但验收无法客观表达，先把验收想清楚，不要急着启动 flow。

## 跑完之后去哪儿

实现和验证发生在隔离 worktree 中，结果保留在 `kp/` 开头的分支上，不会自动进入主干。

当 flow 通过验证后，打开总控台侧栏的“待我处理”，找到对应的合并门，检查改动与验证证据后再确认。具体检查项见[三道人工门](human-gates.md)。

因此，“验证通过但主干没有变化”通常不是故障，而是流程正在等待 C5 人工门 #1。
