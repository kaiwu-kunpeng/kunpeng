# 故障排查：按症状找到诊断与处置

排查时先保存现场：记录原始报错、flow ID、当前分支和 `git status`。不要在原因不明时删除 worktree 或分支。

## 症状一：`serve` 起不来

**诊断**

先读终端中的首个错误。常见原因有三类：端口已经被占用；启动所需的依赖或安全守卫未通过；绑定非回环地址但没有设置访问密码，因此被安全检查拒绝。

**处置**

端口占用时，停止确认无用的占用进程，或改用空闲端口：

```bash
kunpeng serve <端口>
```

依赖守卫失败时，按报错补齐依赖，不要绕过检查。若要绑定非回环地址，先从环境变量或标准输入提供密码，再设置总控台密码：

```bash
kunpeng auth set-password
```

设置后重启 `serve`。只有你明确理解未认证暴露端口的风险时，才考虑显式的不安全放行；不要用于公网，也不要把真实密码写入命令行、脚本或仓库。

## 症状二：总控台终端连不上

**诊断**

总控台终端依赖 `tmux`。系统没有安装 `tmux`，或者启动总控台的进程 PATH 中找不到它，都会导致终端会话创建失败。

**处置**

在运行总控台的同一环境中确认 `tmux` 已安装且可从 PATH 找到。修改服务环境后重启总控台，再重新打开终端；不要只在另一个交互式 shell 中验证。

## 症状三：flow 长时间不前进

**诊断**

先区分三种状态：正在执行、等待人工门、协调状态已经失真。查看总控台当前阶段、最近日志和“待我处理”，确认它是否只是正常等待。

**处置**

需要在安全边界暂停或续跑时使用：

```bash
kunpeng pause <flowId> --repo <目标仓库路径>
kunpeng resume <flowId> --repo <目标仓库路径>
```

若某个实例需要在下一检查点优雅停止，可发送信号：

```bash
kunpeng signal --to <实例名>
```

怀疑协调死流、陈旧产物、幽灵门或孤儿 worktree 时运行：

```bash
kunpeng guardian-report --repo <目标仓库路径>
```

先读报告再处置，不要把“长时间运行”直接等同于“可以删分支”。

## 症状四：合并门报告冲突

**诊断**

常见原因是 flow 的基底已经陈旧：它从较早的主干开始工作，而当前 `main` 已包含并发更新。直接合并可能覆盖新改动或产生文本冲突。

**处置**

保留现有 flow 证据，把分支刷新到当前主干，解决冲突后重新运行原验收与范围检查，再回到合并门。不要在未重验的情况下把冲突标记手工删掉就确认合并。

## 症状五：改动像是被回滚了

**诊断**

先运行 `git status` 确认改动是否已落盘，再核对当前分支、flow 分支和最近提交。镜像同步会以已推送事实为准；合并后若没有按团队流程推送，后续同步可能覆盖只存在本地的结果。

**处置**

先保存 `git status` 和日志证据，确认改动究竟在 worktree、`kp/` 分支、本地主干还是远端。已完成合并后，按团队的推送纪律及时同步共享真相源。原因未明前不要直接删除分支或 worktree，否则会把可恢复问题变成数据丢失。

## 症状六：账号配额耗尽

**诊断**

配额按窗口统计。达到账号上限后，该账号在窗口重置前不会再被选择；如果同一后端的所有可用账号都耗尽，任务会报配额耗尽，并给出最近的预计重置时间。

**处置**

先查看账号状态并做凭证目录预检：

```bash
kunpeng account list
kunpeng account doctor
```

可以等待窗口重置，或在符合团队账号与凭证政策的前提下切换到另一个健康、未耗尽且后端匹配的账号。不要通过伪造用量、共享凭证或放宽目录安全来绕过配额。

## 排查仍无结论时

保留完整错误输出、flow ID、目标仓库、当前阶段、`git status` 和最近一次验收结果。把这些事实一起交给维护者，比只说“卡住了”更容易复现，也能避免误删仍可恢复的现场。
