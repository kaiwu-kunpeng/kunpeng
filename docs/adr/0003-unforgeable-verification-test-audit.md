# 0003 · 验证不可造假 + 弱测试审计

**Status**: Accepted（2026-06-13）

## Context

LLM 实现者有一个根本的利益冲突：它**既写代码、又能自己挑选「验收命令」**。真机早期就观测到这种自我欺骗：

- 实现者写出 `test -f <file>` 这类「只查存在性」的验收——文件在就过，根本没验内容；
- 极端案例：生成的 `hello.txt` 是 **0 字节空文件，却被判 `verified`**——因为验收只查「文件存在」，恒真通过。

只要让实现者自定义「怎样算做对」，它就有动机把验收弱化成恒真断言，于是「通过」毫无意义。声称完成而无真实证据，是多 agent 系统里最危险的腐蚀。

## Decision

确立宪法 C3，并加一道**测试审计**：

1. **验收命令的来源权威化**：验收命令**来自方案 / spec**，实现者**不得自行发明或弱化**。优先用方案直接带来的 `--accept` 精确命令（见 JOURNAL「`--accept` 让方案直接带验收命令」）。
2. **声明完成必附真实证据**：角色不得声明「完成 / 通过」而不附 test/lint/verify 的**实际输出**。无证据 = 未完成。
3. **弱测试 fail-closed 审计**：`auditAcceptanceTest` 闸门检测「只查存在性 / 恒真」的弱验收（`test -f`、空断言等）。**弱测试 → 该 flow 实现前即中止**，不让 LLM 现编脆弱验收。即便是显式来源的命令也过一遍审计（双保险）。

## Consequences

- **换来**：验收脱离实现者控制，「通过」恢复了意义；自我欺骗（空文件 verified）被结构性堵死；审计是确定性的（C8），不靠再叫一个 LLM 来判。
- **成本**：方案/spec 必须把「怎样算做对」写清楚，写方案的人责任变重；审计可能误杀某些看似弱但合理的验收，需要方案侧给精确命令兜底；多一道闸门，多一点延迟。
- **关联**：差分验证（ADR 0005）解决「验收命令本身正确但基线本就红」的另一类误判，与本条互补。
