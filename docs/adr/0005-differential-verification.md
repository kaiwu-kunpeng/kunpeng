# 0005 · 差分验证（只拦基线之外的新错）

**Status**: Accepted（2026-06-14）

## Context

最初的验证门要求「整项目全绿」才算通过：`typecheck` / `lint` / `test` 全部无错才放行。这在玩具仓库成立，在真项目崩溃。

真机首跑对一个真实的 Next.js 线上项目跑首条修复流——只是移除某文件一个未用 import——结果**安全回滚**。复盘发现：**回滚的原因不是我们的改动，而是目标仓的 `npm run typecheck` 基线本来就红**（缺 `@types/jest`，测试文件里 `describe/it/expect` 找不到类型）。也就是说项目在我们动手之前就有一堆既存错误。要求「整项目全绿」，就等于**每一条流都会被既存的基线红误杀回滚**，鲲鹏在真项目上一步都迈不出去（JOURNAL 2026-06-13「真机首跑」「v1 回滚」）。

## Decision

验证门改为**差分验证**：不要求整项目全绿，**只拦「引入了基线之外的新错」的改动**。

- 实现**前**抓一次基线（`typecheck`/相关命令的当前错误集）。
- 实现**后**再跑一次，对比得出 `newFailures` = 实现后有、基线没有的错误。
- `newFailures` 非空才判失败回滚；基线本就有的红，**不归这条流的账**，不误杀。

## Consequences

- **换来**：鲲鹏能在「基线常年带病」的真实活跃库里工作而不被既存问题反复绊倒；验证聚焦「这条改动有没有把事情弄得更糟」，语义正确。真机 v3 用「方案验收 + 差分 typecheck」干净通过，闭环走通。
- **成本**：要先后抓两次基线、做集合对比，比一刀切的「全绿」重；若基线本身在两次抓取间漂移（别的进程改了），差分会有噪声——靠 worktree 隔离（ADR 0001）把漂移面压到最小。
- **边界**：差分验证只解决「基线本就红」的误杀，不解决「验收命令本身写得弱/写错」——后者由测试审计（ADR 0003）和 `--accept` 精确命令负责。两者互补，缺一不可（v2 回滚正是 spec 自拟 grep 验收 `\bcache\b` 撞 `ai-cache` 路径误杀，靠 `--accept` 修，不是差分能修的）。
