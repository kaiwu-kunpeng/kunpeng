# 0006 · 确定性优先于 LLM

**Status**: Accepted（2026-06-13）

## Context

LLM 调用昂贵、慢、且不确定——同一输入两次可能给不同答案，还可能被 prompt 注入带偏。一个研发底座里有大量判定本可以用确定性手段精确得出：「文件存不存在」「类型过不过」「测试绿不绿」「这段文本里有没有这个符号」——这些 grep/lint/test/typecheck 一跑就有确定答案。若把这类判定也交给 LLM，等于在能用尺子量的地方靠目测，既贵又引入不必要的不确定性和被骗空间（参见 ADR 0003 的弱测试自欺）。

## Decision

确立宪法 C8：**能用确定性手段（grep / lint / test / 类型检查）判定的，绝不调用 LLM。LLM 只在确定性手段无法判定时介入。**

落到具体设计（Block-A 方案接入）：

- **方案分解**全确定性——`plan/parse.ts` 是纯函数，按 markdown 标题层级/checklist 自适应切分，id 由结构决定、可复现，不调 LLM。
- **阶段切边界**确定性——最浅标题层=阶段，深一层/checklist=flow，纯结构计算。
- **验收提取**优先纯函数 `extractAcceptance`（找 ` ```accept ` 块或 `验收:` 行）。
- **唯一允许 LLM 介入处**：无显式验收时，用小 agent 把「做什么 + 验收标准」**翻译**成一条可执行验收命令——这是确定性手段确实做不到的自然语言理解。而且翻译结果还要过确定性的弱测试审计（C3）。

## Consequences

- **换来**：判定快、稳、可复现、省 token，且不给 prompt 注入留判定入口；同一方案分解出的 flow id 稳定可复现，利于调试与缓存。
- **成本**：纯函数分解器要覆盖各种 markdown 结构的边界情形（无标题、扁平 checklist、深浅混排），写起来比「丢给 LLM 看着办」累；对不规整的方案，确定性切分可能不如 LLM 灵活——靠「自适应」算法和验收翻译这唯一 LLM 出口兜底。
- **约束**：新增任何判定逻辑，先问「能不能 grep/test/typecheck 出来」，能就不准调 LLM。
