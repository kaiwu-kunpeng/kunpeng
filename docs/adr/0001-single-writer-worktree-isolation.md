# 0001 · 单写者 + worktree 隔离

**Status**: Accepted（2026-06-13）

## Context

鲲鹏是「一个主 agent + 按需子 agent」的多角色协作底座，多条开发流可能同时在进行（一个方案被分解成 N 条 flow，段内并行）。若多个角色/进程同时往同一份工作树写代码，会互相覆盖、产生半截状态、让「谁改了什么」不可追溯——这正是多 agent 系统最常见的崩法。

同时，协作里还有评审、审计、守护等多种角色，它们都会「想动代码」。如果允许发现问题的角色顺手就改，写权限就扩散到全员，回滚边界和责任边界一起糊掉。

## Decision

1. **单写者**：任一时刻，一条工作流的代码**写锁只属于「开发循环」的实现角色一人**。其他任何角色/组（评审、审计、守护、规划）**不得直接改代码**，只能产出「发现」与「提案」。这是宪法 C1。
2. **worktree 隔离**：并行开发流各自跑在独立的 `git worktree`（`.kunpeng/wt/<flowId>`）里，off 各自的 base 分叉，互不踩踏。验证过的产出留在 `kp/<flow>` 分支。
3. **写锁用文件系统锁**（跨进程互斥，非进程内变量），因为子 agent 是独立后端 CLI 进程，进程内锁挡不住跨进程并发（见 JOURNAL 2026-06-13「单写者改文件系统锁」）。

## Consequences

- **换来**：并行无踩踏；每条流的改动天然落在自己分支/worktree，回滚粒度干净（支撑 C4 可逆性）；写权限集中=责任清晰，评审/审计角色越权改代码这条路被结构性堵死。
- **成本**：每条 flow 要起一个 worktree，有创建/清理开销与磁盘占用；合并要专门的安全合并路径（见 ADR 0009 的 `safeMerge`），不能在共享工作树上 `git checkout`（那次「合并夺工作树」事件正是旧逻辑违反此点，见 JOURNAL「合并事件复盘」）。
- **约束**：任何新角色加入都必须想清楚它是「写者」还是「提案者」，默认是后者。
