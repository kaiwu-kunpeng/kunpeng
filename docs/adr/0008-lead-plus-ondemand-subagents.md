# 0008 · 主 + 按需子 agent，不养固定编制

**Status**: Accepted（2026-06-13）

## Context

鲲鹏的可视化方案（`index.html`）画了一张「数字研发团队」org chart，列了像是 33 个角色的花名册。有一种诱人但危险的实现方式：照字面把它做成 33 个**常驻、固定、互相聊天**的 agent，让它们像真公司一样开会协作。

ChatDev 等「拟人化多 agent 互聊」系统已经反复证明这条路的脆性：固定编制的 agent 互相对话会累积上下文噪声、角色幻觉、无意义的礼貌往返，错误在对话链里放大，整个系统撞上「脆性墙」——规模一上去就不可控。把 org chart 当军规执行，等于主动给自己砌这堵墙。

## Decision

确立宪法 C9：**真实结构是「一个主 agent + 按需子 agent」，不是固定 33 人编制。**

- **主 agent** 持目标 / 进度 / 底线，负责分解派活。
- **子 agent 按需起**：领一个短目标、干完回一份摘要即弃，不常驻、不互相闲聊。
- 花名册与角色是**按需实例化的能力 playbook**，不是「必须全员到岗」的军规。org chart 是**示意**（能力地图），不是字面编制。
- **简单需求可不起子 agent、直接做**——不为了「像个团队」而强行摆开阵仗。

## Consequences

- **换来**：避开 ChatDev 式脆性墙——没有常驻 agent 间的噪声累积与角色幻觉；起灭按需，省 token、省协调开销；扩展性来自「需要时实例化能力」而非「养更多编制」。
- **成本**：org chart 与实际运行结构**不是一一对应**，新人看图可能误以为真有 33 个常驻角色——需在文档里反复澄清「示意 ≠ 编制」（本 ADR 即澄清之一）。
- **关联**：与 C2 制品即真相（0002）配套——子 agent 完成即弃，状态靠落盘产物而非常驻记忆传递，正因为子 agent 不常驻，才更不能依赖会话内存。
